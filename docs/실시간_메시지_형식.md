# 운동방 실시간 메시지 형식 (초안)

> S2(이슈 #2) 합의용 초안이다. 프론트·3D 담당이 확인하면 "초안"을 지운다. 이후 슬라이스(S4 동작 정보, S6 응원)는 이 봉투에 메시지 종류만 더한다.
> 실시간 서버는 **내용을 해석하지 않고 같은 방에 전달만** 한다. 운동 기록(DB)은 만들거나 바꾸지 않는다. 운동 시작·종료는 프론트가 REST로 직접 호출한다(이슈 #7 합의).

## 연결 흐름

1. 참가자 생성 `POST /api/participants` → 응답의 `clientToken`을 기기에 보관한다.
2. REST 입장 `POST /api/rooms/{roomId}/enter` (헤더 `X-Participant-Token`).
3. WebSocket 연결: 로컬 `ws://localhost:8080/ws`, 운영 `wss://{도메인}/ws`.
4. 연결되면 **10초 안에** `JOIN`을 보낸다. 토큰은 URL이 아니라 이 메시지로 보낸다(프록시 접근 로그에 남지 않게).
5. 서버가 `ROOM_SNAPSHOT`으로 방 전체 상태를 보내 준다. 이후 다른 참가자의 변화는 이벤트로 온다.
6. **10초마다 `PING`**을 보낸다. 30초 동안 아무 메시지가 없으면 서버는 연결 불안정으로 보고 연결을 닫는다.
7. 나갈 때는 `LEAVE`를 보낸다. 보내지 않고 끊기면 30초 동안 자리를 남겨 두고 재접속을 기다린다.

```text
프론트                                   서버
  │ POST /api/rooms/1/enter ──────────────▶ │ (참가자를 운동방에 연결)
  │ ws 연결 /ws ──────────────────────────▶ │
  │ JOIN {token, roomId} ─────────────────▶ │ 토큰·방·REST 입장·정원 확인
  │ ◀──────────────── ROOM_SNAPSHOT         │
  │                   PARTICIPANT_JOINED ──▶ (같은 방 다른 참가자)
  │ STATUS {exercise, progressStatus} ────▶ │
  │                   PARTICIPANT_STATUS ──▶ (같은 방 다른 참가자)
  │ PING ─────────────────────────────────▶ │
  │ ◀──────────────────────────── PONG      │
  │ LEAVE ────────────────────────────────▶ │
  │                   PARTICIPANT_LEFT ────▶ (같은 방 다른 참가자)
```

## 공통 봉투

### 클라이언트 → 서버

```json
{ "type": "STATUS", "payload": { } }
```

- `type`과 `payload`만 보낸다. `roomId`·`participantId`를 보내도 **JOIN 이후에는 무시한다.** 서버는 연결에 묶인 참가자로만 처리한다(다른 참가자인 척하는 메시지 차단).

### 서버 → 클라이언트

```json
{
  "type": "PARTICIPANT_STATUS",
  "roomId": 1,
  "participantId": 3,
  "sentAt": "2026-11-09T12:00:00.123Z",
  "payload": { }
}
```

| 필드 | 타입 | 뜻 |
|---|---|---|
| `type` | string | 메시지 종류 |
| `roomId` | number \| null | 운동방 식별값. 다른 방 메시지이거나 입장 전 오류면 `null` |
| `partyId` | number \| null | 공개 파티 식별값(이슈 #11). 다른 방 메시지이거나 입장 전 오류면 `null` |
| `contestGameId` | number \| null | 챌린지 판 식별값(이슈 #34). 다른 방 메시지이거나 입장 전 오류면 `null` |
| `participantId` | number \| null | 이 이벤트의 주인공. 챌린지 판은 `playerId`. `ROOM_SNAPSHOT`은 입장한 본인. 입장 전 오류면 `null` |
| `sentAt` | string | 서버가 이벤트를 만든 시각 (ISO-8601, UTC) |
| `payload` | object \| null | 종류별 내용. `PONG`은 `null` |

- 재방문 토큰은 **어떤 서버 메시지에도 들어가지 않는다.**
- 같은 참가자의 이벤트는 보낸 본인에게 다시 오지 않는다(본인 화면은 본인이 이미 안다). 단, `ROOM_SNAPSHOT`에는 본인도 들어 있다.

## 클라이언트가 보내는 메시지

### `JOIN` — 운동방 입장

```json
{ "type": "JOIN", "payload": { "token": "3f1c…", "roomId": 1 } }
```

| 필드 | 필수 | 뜻 |
|---|---|---|
| `token` | △ | 참가자 생성 때 받은 재방문 토큰. 운동방·공개 파티 입장에 필수 |
| `roomId` | △ | REST 입장을 마친 운동방 식별값. `roomId`·`partyId`·`contestGameId` 중 **하나만** 보낸다 |
| `partyId` | △ | 공개 파티 식별값(이슈 #11). 아래 "공개 파티" 참고. 둘 이상 함께 보내면 `INVALID_MESSAGE` |
| `contestGameId` | △ | 챌린지 판 식별값(이슈 #34). 아래 "학교 대항 스쿼트 챌린지 판" 참고 |
| `playerId` | △ | 챌린지 판 참가 식별값. `contestGameId`와 함께 필수, `token`은 보내지 않는다 |

- 같은 토큰으로 다시 `JOIN`하면(재접속·새 창) **진행 상태를 유지한 채** 새 연결로 바뀐다. 예전 연결은 `SESSION_REPLACED`로 닫힌다.

### `STATUS` — 내 현재 운동·진행 상태

```json
{ "type": "STATUS", "payload": { "exerciseId": 3, "exerciseName": "스쿼트", "progressStatus": "EXERCISING" } }
```

| 필드 | 타입 | 필수 | 뜻 |
|---|---|---|---|
| `exerciseId` | number \| null | - | 현재 운동 식별값(루틴의 운동 ID). 아직 없으면 `null` |
| `exerciseName` | string \| null | - | 화면 표시용 운동 이름, 최대 50자 |
| `progressStatus` | string | O | 아래 진행 상태 중 하나 |

진행 상태 `progressStatus` (이슈 #7 공통 계약)

| 값 | 뜻 |
|---|---|
| `WAITING` | 입장 후 운동 시작 전 대기. **입장 직후 기본값** |
| `EXERCISING` | 운동 진행 중 |
| `RESTING` | 운동 간 전환·휴식 |
| `FINISHED` | 루틴을 마침. **종료 REST(`POST /api/workouts/{id}/finish`)가 성공한 뒤에만** 보낸다 |
| `CAMERA_ERROR` | 카메라 권한 거부·장치 오류 |

- 서버는 이 값을 해석하지 않는다. 운동 이름이 루틴과 맞는지 확인하지 않는다.
- 다른 참가자의 상태로 내 상태가 바뀌는 일은 없다. 내 상태는 내 `STATUS`로만 바뀐다.

### `POSE` — 내 동작 정보 (이슈 #4)

```json
{ "type": "POSE", "payload": { "landmarks": [[0.012, -0.531, 0.104, 0.98], [0.153, -0.402, 0.061, 0.97]] } }
```

| 필드 | 타입 | 필수 | 뜻 |
|---|---|---|---|
| `landmarks` | number[][] | O | 관절 배열. 관절 하나는 `[x, y, z]` 또는 `[x, y, z, visibility]`. 관절 1~33개 |

- 서버는 **모양만** 검사한다(관절 1~33개, 관절 하나가 숫자 3~4개). 좌표 범위·관절 순서는 보지 않는다. 관절 목록·순서는 [동작정보_형식.md](동작정보_형식.md)에서 AI·3D가 정한다.
- 메시지 하나는 **2KB 이하**(`realtime.pose-max-bytes`). 넘거나 모양이 틀리면 `INVALID_MESSAGE`를 받는다(연결 유지).
- 참가자 한 명당 **최근 1초 동안 15개까지** 중계한다(`realtime.pose-max-per-second`). 넘는 메시지는 **오류 없이 버린다.** 버린 메시지도 연결 유지 신호로는 센다.
- 진행 상태가 `CAMERA_ERROR`인 동안 보낸 `POSE`는 **오류 없이 버린다.** 다른 참가자에게 전달되지 않는다.
- 인식이 안 되는 동안에는 보내지 않는다. 서버가 대신 만들어 보내는 동작 정보는 없다.
- `landmarks` 외의 필드는 다른 참가자에게 전달되지 않는다.
- **서버는 동작 정보를 저장하지 않는다.** DB에도, 방 상태에도 남지 않으므로 `ROOM_SNAPSHOT`에는 들어 있지 않다. 새로 들어온 참가자는 다음 `POSE`부터 받는다.

### `CHEER` — 친구에게 응원 보내기 (이슈 #6)

```json
{ "type": "CHEER", "payload": { "targetParticipantId": 4, "reaction": "FIRE" } }
```

| 필드 | 타입 | 필수 | 뜻 |
|---|---|---|---|
| `targetParticipantId` | number | O | 응원받을 친구. 클릭한 캐릭터의 `participantId` |
| `reaction` | string | O | 리액션 코드. **영문 대문자·숫자·밑줄 1~30자** (예: `FIRE`, `CLAP`) |

- 대상 **한 명에게만** 전달한다(1:1). 같은 방의 다른 참가자에게는 가지 않는다.
- 성공하면 대상은 `CHEER_RECEIVED`, 보낸 본인은 `CHEER_SENT`를 받는다.
- 대상이 방에 없거나(퇴장·다른 방) 연결 불안정이면 `CHEER_TARGET_UNAVAILABLE` 오류를 받는다. 연결은 유지된다.
- **같은 친구에게 1초 안에 다시 보내면 연타로 보고 오류 없이 무시한다**(`realtime.cheer-cooldown`). `CHEER_SENT`도 오지 않는다. 다른 친구에게는 바로 보낼 수 있다.
- 자기 자신을 대상으로 하거나 리액션 코드 형식이 틀리면 `INVALID_MESSAGE`.
- 리액션 종류는 디자인·PM이 정한다. 서버는 목록과 맞춰 보지 않고 코드 형식만 확인해 그대로 전달·저장한다.
- 전달된 응원만 저장한다(보낸 사람, 받은 사람, 리액션, 이벤트 시각). 실패하거나 무시된 응원은 저장하지 않는다.

### `PING` — 연결 유지

```json
{ "type": "PING" }
```

- JOIN 전에도 보낼 수 있다. 서버는 `PONG`으로 답한다. 10초 간격을 권장한다.

### `LEAVE` — 퇴장

```json
{ "type": "LEAVE" }
```

- 바로 방에서 빠지고 서버가 연결을 닫는다. 다른 참가자에게 `PARTICIPANT_LEFT`(`reason: LEFT`)가 간다.

## 서버가 보내는 메시지

### `ROOM_SNAPSHOT` — 입장한 본인에게 방 전체 상태

```json
{
  "type": "ROOM_SNAPSHOT", "roomId": 1, "participantId": 3, "sentAt": "…",
  "payload": {
    "capacity": 5,
    "participants": [
      {
        "participantId": 3, "nickname": "주영", "characterCode": "CHARACTER_01",
        "exerciseId": null, "exerciseName": null,
        "progressStatus": "WAITING", "connectionStatus": "CONNECTED"
      }
    ],
    "reconnected": false
  }
}
```

- `participants`는 본인을 포함한 입장 순서 목록이다. 연결 불안정으로 재접속을 기다리는 참가자도 들어 있다.
- 닉네임은 중복될 수 있다. **참가자 구분은 `participantId`로만 한다.**
- `reconnected` (이슈 #7): 이미 방에 자리가 있던 참가자가 새 연결로 돌아왔으면(재접속·새 창) `true`, 처음 입장이면 `false`.
  `true`면 목록 안의 본인 상태는 끊기기 전 마지막 값을 그대로 복원한 것이다. 아래 "끊김과 재접속"을 따른다.

### `PARTICIPANT_JOINED` — 다른 참가자 입장

`payload`는 `ROOM_SNAPSHOT.participants`의 항목 하나와 같은 형식이다.

### `PARTICIPANT_STATUS` — 다른 참가자의 운동·진행 상태 변경

`payload`는 `STATUS`의 `payload`와 같은 형식이다(`exerciseId`, `exerciseName`, `progressStatus`).

### `PARTICIPANT_POSE` — 다른 참가자의 동작 정보 (이슈 #4)

```json
{ "type": "PARTICIPANT_POSE", "roomId": 1, "participantId": 3, "sentAt": "…",
  "payload": { "landmarks": [[0.012, -0.531, 0.104, 0.98], [0.153, -0.402, 0.061, 0.97]] } }
```

- `payload`는 보낸 사람의 `POSE.payload.landmarks`를 그대로 담는다. 숫자를 고치지 않는다.
- 보낸 본인에게는 오지 않는다. 본인 캐릭터는 본인 인식 결과로 바로 움직인다.
- 이 메시지가 멈추면 받는 쪽은 **마지막 자세에서 멈추고 움직임을 지어내지 않는다.** 멈춘 이유는 아래로 구분한다.
  - 친구 진행 상태가 `CAMERA_ERROR`: 카메라 미허용
  - 친구 연결 상태가 `UNSTABLE`: 연결 불안정
  - 둘 다 아니면 인식이 끊긴 것(표시 방법은 [동작정보_형식.md](동작정보_형식.md) "정해야 할 것")

### `CHEER_RECEIVED` — 나에게 온 응원 (이슈 #6)

```json
{ "type": "CHEER_RECEIVED", "roomId": 1, "participantId": 3, "sentAt": "…",
  "payload": { "targetParticipantId": 4, "reaction": "FIRE" } }
```

- **받은 사람에게만** 온다. 봉투의 `participantId`가 **보낸 사람**이다. 화면에 "누가 응원했는지"를 이 값으로 표시한다.
- `payload.targetParticipantId`는 받은 본인이다.

### `CHEER_SENT` — 내 응원이 전달됨 (이슈 #6)

```json
{ "type": "CHEER_SENT", "roomId": 1, "participantId": 3, "sentAt": "…",
  "payload": { "targetParticipantId": 4, "reaction": "FIRE" } }
```

- **보낸 본인에게만** 온다. `payload.targetParticipantId`로 응원한 대상을 화면에서 확인시킨다.
- `sentAt`은 대상이 받은 `CHEER_RECEIVED`의 `sentAt`과 같다.

### `CONNECTION_STATUS` — 다른 참가자의 연결 상태 변경

```json
{ "type": "CONNECTION_STATUS", "participantId": 4, "payload": { "connectionStatus": "UNSTABLE" } }
```

| 값 | 뜻 |
|---|---|
| `CONNECTED` | 정상 연결(재접속하면 이 값으로 다시 온다) |
| `UNSTABLE` | 연결이 끊겼거나 30초간 응답이 없음. **마지막 진행 상태를 현재처럼 단정해 표시하지 않는다** |

- 내 연결 문제는 브라우저의 WebSocket `close` 이벤트로 알고, 친구의 연결 문제는 이 메시지로 안다. 둘을 구분해 표시한다.

### `PARTICIPANT_LEFT` — 다른 참가자 퇴장

```json
{ "type": "PARTICIPANT_LEFT", "participantId": 4, "payload": { "reason": "TIMEOUT" } }
```

| `reason` | 뜻 |
|---|---|
| `LEFT` | `LEAVE`를 보내 직접 나감 |
| `TIMEOUT` | 연결이 끊긴 뒤 30초 안에 돌아오지 않음 |

### `PONG`

`PING`에 대한 응답. `payload`는 `null`.

### `ERROR`

```json
{ "type": "ERROR", "roomId": null, "participantId": null, "sentAt": "…",
  "payload": { "code": "ROOM_FULL", "message": "운동방 정원이 가득 찼습니다.", "closed": true } }
```

- `closed`가 `true`면 서버가 곧 연결을 닫는다. 실패 안내와 **재시도 수단**을 보여준다.
- 내부 예외 메시지는 담지 않는다.

| `code` | 닫힘 | 언제 | 프론트 처리(제안) |
|---|---|---|---|
| `INVALID_MESSAGE` | X | JSON이 아니거나, 종류를 모르거나, 필수 값 누락·형식 오류, `POSE`가 2KB 초과·모양 오류 | 개발 중 버그. 콘솔에 남긴다 |
| `JOIN_REQUIRED` | X | JOIN 전에 STATUS·POSE 등을 보냄 | JOIN부터 다시 |
| `ALREADY_JOINED` | X | 같은 연결에서 JOIN을 또 보냄 | 무시 |
| `PARTICIPANT_NOT_FOUND` | O | 토큰에 해당하는 참가자가 없음 | 프로필 설정으로 보낸다 |
| `ROOM_NOT_FOUND` | O | 운동방이 없음 | 홈으로 |
| `NOT_ENTERED_ROOM` | O | REST 입장을 하지 않은 방 | REST 입장 후 재연결 |
| `PUBLIC_PARTY_NOT_FOUND` | O | `partyId`가 지금 공개 파티와 다름 | 홈으로. 상태 API를 다시 조회 |
| `PUBLIC_PARTY_CLOSED` | O | 공개 파티가 닫힌 시간에 `JOIN`(재접속 포함) | "지금은 열려 있지 않아요" + 다음 오픈 시각 안내 |
| `CONTEST_GAME_NOT_FOUND` | O | `contestGameId`에 해당하는 챌린지 판이 없음 | 참가(`join`)부터 다시 |
| `CONTEST_PLAYER_NOT_FOUND` | O | `playerId`가 그 판의 참가자가 아님(나갔거나 다른 판) | 참가(`join`)부터 다시 |
| `CONTEST_GAME_FINISHED` | O | 이미 끝난(`FINISHED`) 판에 `JOIN`(재접속 포함) | 재연결하지 않는다. 결과 화면 유지 |
| `ROOM_FULL` | O | 정원이 찼음(연결 불안정 참가자 자리 포함) | 정원 안내 + 재시도 |
| `SESSION_REPLACED` | O | 같은 참가자가 다른 창으로 입장함 | "다른 창에서 입장했어요" 안내. 자동 재연결하지 않는다 |
| `JOIN_TIMEOUT` | O | 연결 후 10초 안에 JOIN이 없음 | 재연결 |
| `CHEER_TARGET_UNAVAILABLE` | X | 응원 대상이 방에 없거나(퇴장·다른 방) 연결 불안정 | "친구가 지금 연결되어 있지 않아요" 안내. 운동 화면은 그대로 둔다 |
| `INTERNAL_ERROR` | X | 서버 오류 | 재시도 안내 |

### 연결 닫힘 코드

서버가 연결을 닫을 때 WebSocket 닫힘 코드와 사유(`reason`)로 원인을 알 수 있다.

| 코드 | 사유 | 언제 | 프론트 처리(제안) |
|---|---|---|---|
| `1000` | (없음) | `LEAVE`를 보냄 | 정상 퇴장 |
| `1008` | `ERROR`의 `code`와 같음 (예: `ROOM_FULL`) | `closed: true`인 `ERROR` 직후 | 위 표의 처리를 따른다 |
| `4500` | `HEARTBEAT_TIMEOUT` | 30초 동안 아무 메시지가 없음 | 재연결 후 같은 토큰으로 `JOIN` (진행 상태는 유지됨) |
| `1000` | `CONTEST_GAME_FINISHED` | 챌린지 판이 `FINISHED`가 됨(이슈 #34). `ERROR` 없이 닫는다 | 재연결하지 않는다. 결과는 REST로 조회 |

- 코드 없이 끊기면(`1006`) 네트워크 문제다. 재연결 후 `JOIN`한다.

- 출처(Origin)가 `cors.allowed-origins`에 없으면 연결 단계(handshake)에서 HTTP 403으로 거절된다. 이때는 메시지가 오지 않는다.
- 텍스트 메시지 하나는 8KB를 넘지 않게 보낸다(Tomcat 기본 한도). 동작 정보는 이 한도 안에 들도록 형식을 줄인다([동작정보_형식.md](동작정보_형식.md)).

## 끊김과 재접속 (이슈 #7)

개인 운동 진행은 **본인 화면이 주인**이다. 서버는 본인 `STATUS`로만 그 참가자의 상태를 바꾸고, 다른 참가자의 시작·종료·퇴장·끊김으로는 바꾸지 않는다(`RoomIndependenceTest`로 고정).

| 일어난 일 | 내 화면 | 친구 화면 |
|---|---|---|
| 친구가 먼저 끝냄(`FINISHED`) | 아무 영향 없음. 내 루틴 계속 | - |
| 친구가 퇴장(`LEAVE`·`TIMEOUT`) | `PARTICIPANT_LEFT`만 온다. 내 상태·연결은 그대로 | - |
| 친구 연결이 끊김 | 친구가 주인공인 `CONNECTION_STATUS(UNSTABLE)`. **친구 캐릭터에만** "연결 불안정" 표시 | - |
| 내 연결이 끊김 | 브라우저 WebSocket `close` 이벤트(코드 `1006`·`4500`). **내 화면 상단에** "연결이 끊겼어요" 표시. 운동 진행은 멈추지 않는다 | 나를 주인공으로 한 `CONNECTION_STATUS(UNSTABLE)` |
| 내가 30초 안에 다시 연결 | `reconnected: true` 스냅샷 | `CONNECTION_STATUS(CONNECTED)` |
| 30초 안에 못 돌아옴 | 다시 연결하면 처음 입장처럼 `reconnected: false` | `PARTICIPANT_LEFT(TIMEOUT)` |

- **내 연결 문제와 친구 연결 문제는 신호가 다르다.** 서버는 본인에게 본인의 `CONNECTION_STATUS`를 보내지 않는다. 내 문제는 내 연결의 `close`로만, 친구 문제는 친구가 주인공인 `CONNECTION_STATUS`로만 안다.
- 재접속 순서: 연결 → 같은 토큰으로 `JOIN` → `reconnected: true` 스냅샷 수신 → **본인의 지금 상태를 `STATUS`로 한 번 보낸다.**
  끊긴 동안 본인 화면에서 진행이 바뀌었을 수 있기 때문이다. 서버는 끊긴 동안의 상태를 짐작해 만들지 않는다.
- 끊긴 동안의 동작 정보·상태 변경은 서버가 만들어 보내지 않는다. 친구 화면의 내 캐릭터는 마지막 자세에서 멈춰 있다가 다음 `POSE`부터 움직인다.
- 다른 창으로 밀려난 예전 연결(`SESSION_REPLACED`)로 늦게 도착한 `STATUS`·`POSE`는 전달하지 않는다.
- 진행 상태는 위 표의 다섯 값만 받는다. 일시정지(`PAUSED` 등)처럼 승인되지 않은 값은 `INVALID_MESSAGE`다. `restSeconds`처럼 정의되지 않은 필드는 저장·전달하지 않고 버린다. 휴식 길이·일시정지는 PM 확정 후 추가한다.
- 운동 기록(`Workout`)은 실시간 서버가 건드리지 않는다. 끊겨도 기록은 진행 중으로 남고, 종료 REST가 성공한 뒤에만 `FINISHED`를 보낸다(이슈 #7 A/B 합의).

## 2회차 재입장 (이슈 #9)

1회차 결과 화면에서 2회차 추천(`POST /api/routines/next-round`)을 받은 뒤 같은 운동방으로 다시 들어가는 흐름이다.

1. REST 입장 `POST /api/rooms/{roomId}/enter`를 다시 호출한다(같은 방이면 그대로 성공).
2. 연결이 살아 있으면 그대로 쓰고, 끊었다면 새로 연결해 `JOIN`한다.
   - 결과 화면에서 `LEAVE`로 나갔거나 30초가 지났으면 처음 입장처럼 `WAITING`으로 시작한다(`reconnected: false`).
   - 30초 안에 돌아왔으면 1회차 마지막 상태(`FINISHED`)가 복원된 채 들어온다(`reconnected: true`).
3. 2회차 루틴의 첫 운동으로 `STATUS`를 보낸다. `exerciseId`는 **2회차 루틴의 운동 식별값**(새 루틴이라 1회차와 다르다)이다.
   서버는 받은 값으로 바로 바꾸고 친구에게 `PARTICIPANT_STATUS`를 보낸다. `FINISHED` 다음에 `WAITING`·`EXERCISING`이 와도 거절하지 않는다.
4. 친구 화면에는 같은 참가자(`participantId` 동일)가 새 운동으로 표시된다. 운동 순서와 수행량은 프론트가 2회차 루틴 응답을 따른다. 서버는 루틴과 맞는지 확인하지 않는다.

## 공개 파티 (이슈 #11, P1)

밤에 열리는 공개 선셋 운동장이다. 친구 파티 운동방과 **같은 연결(`/ws`)과 같은 메시지**를 쓰고, 다음만 다르다.

| 항목 | 친구 파티 운동방 | 공개 파티 |
|---|---|---|
| 입장 전 REST | `POST /api/rooms/{roomId}/enter` 필요 | **필요 없음.** 참가자(임시 프로필)만 있으면 된다 |
| `JOIN` | `{ token, roomId }` | `{ token, partyId }` |
| 정원 | 5명(`ROOM_FULL`) | **없음.** `ROOM_SNAPSHOT.payload.capacity`가 `null` |
| 봉투 | `roomId` 채움, `partyId: null` | `partyId` 채움, `roomId: null` |
| 입장 시간 | 언제나 | 열려 있을 때만. 닫혀 있으면 `PUBLIC_PARTY_CLOSED` |
| 응원 | 전달 + 저장 | 전달만 한다(응원 저장은 운동방 기준) |

- 운동방과 공개 파티는 식별값이 같아도 **별개 공간**이다. 서로의 입장·상태·동작 정보가 넘어가지 않는다.
- 참가자마다 진행 상태는 독립이다. 한 사람의 시작·종료·퇴장이 다른 사람의 진행을 바꾸지 않는다.
- 이미 들어와 있던 참가자는 종료 시각이 지나도 **내보내지 않는다**(하던 운동은 끝까지). 다만 닫힌 뒤에는 재접속 `JOIN`도 거부한다.
- 실시간 서버는 공개 파티 운동 기록을 만들지 않는다. 기록 저장은 데이터 담당(B)이 정한다.

### 오픈 상태 조회 — `GET /api/public-parties/current`

```json
{
  "resultCode": "200-1", "msg": "공개 파티 상태를 조회했습니다.",
  "data": {
    "partyId": 1, "name": "선셋 에어로빅", "status": "OPEN",
    "opensAt": "2026-11-11T22:00:00+09:00", "closesAt": "2026-11-11T23:00:00+09:00",
    "participantCount": 3
  }
}
```

- `status`가 `OPEN`일 때만 홈 카드에 입장 버튼을 켠다. `CLOSED`면 `opensAt`(다음 오픈 시각)을 안내하고 참여 중처럼 보이지 않게 한다.
- `participantCount`는 지금 실시간 방에 있는 인원(재접속 대기 포함)이다.
- 시각은 설정값이다. 기획서의 "밤 10시"는 PM 확정 전이라 **임시값 22:00 ~ 23:00(Asia/Seoul, 매일)**로 둔다.
  설정 키 `public-party.open-time`·`close-time`·`zone`·`days`, 환경 변수 `PUBLIC_PARTY_OPEN_TIME`·`PUBLIC_PARTY_CLOSE_TIME`·`PUBLIC_PARTY_ZONE`.
  종료가 오픈보다 이르면(예: 22:00 ~ 00:30) 자정을 넘겨 닫는다.

- 오류·비정상 종료는 모든 경우 0개였다. 입장·상태 공유(`STATUS`)는 빈도가 낮아 50명에서도 영향이 작다(`PublicPartyIntegrationTest` 20명 확인).

## 학교 대항 스쿼트 챌린지 판 (이슈 #34)

시연장 이벤트 화면 `/univ-contest`의 판 참가자를 3D 캐릭터로 서로 보이게 하는 경로다. 친구 파티 운동방과 **같은 연결(`/ws`)과 같은 메시지**를 쓰고, 다음만 다르다.

```json
{ "type": "JOIN", "payload": { "contestGameId": "17", "playerId": "41" } }
```

| 항목 | 친구 파티 운동방 | 챌린지 판 |
|---|---|---|
| 입장 전 REST | `POST /api/rooms/{roomId}/enter` | `POST /api/univ-contest/games/join` (받은 `gameId`·`playerId`를 그대로 보낸다) |
| `JOIN` | `{ token, roomId }` | `{ contestGameId, playerId }` — 토큰 없음. 문자열 `"17"`·숫자 `17` 모두 받는다 |
| 신원 확인 | 토큰의 참가자가 그 방에 REST 입장했는지 | `playerId`가 그 판의 참가자인지만 본다 |
| 정원 | 5명 | 판의 `maxPlayers`(4명). `ROOM_SNAPSHOT.payload.capacity`가 `4` |
| 봉투 | `roomId` 채움 | `contestGameId` 채움, `roomId`·`partyId`는 `null` |
| `participantId` | 참가자 식별값 | 판 참가 식별값(`playerId`). REST 응답은 문자열, 여기서는 숫자다 |
| 표시 이름 | 닉네임·캐릭터 | 판의 `nickname`. 캐릭터를 고르지 않아 `characterCode`는 `null` |
| 응원 | 전달 + 저장 | 쓰지 않는다(보내면 전달만 하고 저장하지 않는다) |
| 끝날 때 | 계속 유지 | 판이 `FINISHED`가 되면 1초 안에 서버가 모두를 `1000 CONTEST_GAME_FINISHED`로 닫는다 |

- `ROOM_SNAPSHOT`·`PARTICIPANT_JOINED`·`PARTICIPANT_LEFT`·`PARTICIPANT_STATUS`·`PARTICIPANT_POSE`·`CONNECTION_STATUS`·재접속은 친구 파티 운동방과 같다.
- 관절 좌표는 지금처럼 **저장하지 않고 중계만** 한다. 횟수 집계는 REST `result`로만 한다(실시간 메시지는 횟수에 영향 없음).
- 판에서 나가기(REST `leave`)는 실시간 연결을 닫지 않는다. 화면을 떠날 때 `LEAVE`도 함께 보낸다.
- **신원 확인이 약하다.** 토큰이 없어서 남의 `playerId`를 알면 대신 들어올 수 있다. 시연장 노트북 4대 전용이라 받아들였다. 막아야 하면 `join` 응답에 판 전용 토큰을 하나 더 주는 방법이 있다(아래 "정해야 할 것").

## 임시값 (PM 확인 필요)

| 항목 | 임시 값 | 설정 키 | 사유 |
|---|---|---|---|
| JOIN 대기 | 10초 | `realtime.join-timeout` | 연결만 열고 입장하지 않는 연결 정리 |
| 응답 없음 판단 | 30초 (PING 10초 권장) | `realtime.heartbeat-timeout` | 탭 닫힘 없이 네트워크만 끊긴 경우 감지 |
| 재접속 대기 | 30초 | `realtime.reconnect-grace` | 잠깐 끊긴 참가자가 자리를 잃지 않게 |
| 정원 | 5명 (DB `room.capacity`) | - | 기획서 "친구 2~5명". 이슈 #2 B 임시값 |
| 동작 정보 크기 | 2KB (2048바이트) | `realtime.pose-max-bytes` | 관절 33개·소수 3자리가 약 0.9KB. 여유를 두고 결과 그대로(약 9KB) 보내는 실수를 막는다 |
| 동작 정보 빈도 | 참가자당 1초에 15개 | `realtime.pose-max-per-second` | [동작정보_형식.md](동작정보_형식.md)의 측정 기준. 한 명의 과도한 전송이 방 전체를 막지 않게 |
| 공개 파티 시간 | 매일 22:00 ~ 23:00 (Asia/Seoul) | `public-party.*` | 기획서 "밤 10시쯤". 오픈·종료 시각, 요일, 시간대 PM 확정 전 |
| 응원 연타 제한 | 같은 친구에게 1초에 1번 | `realtime.cheer-cooldown` | 기능명세 6.1 "중복·연타 처리는 개발팀 설계". 대상마다 따로 센다 |
