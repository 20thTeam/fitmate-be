# 동작 정보(Pose) 형식 제안 (초안)

> S3(이슈 #3) 합의용 초안이다. 백엔드(실시간)가 **운동방에 그대로 중계할 수 있는 크기·빈도**를 재서 제안한다.
> 관절 종류와 좌표계는 AI·3D 담당이 정하고, 이 문서는 그 선택이 서버 중계 한도 안에 드는지 판단하는 근거다.
> 중계 구현(메시지 종류 추가, 빈도 상한, 카메라 미허용 참가자 제외)은 S4(이슈 #4)에서 한다.

## 서버가 하는 일과 하지 않는 일

- 같은 운동방의 다른 참가자에게 **그대로 전달만** 한다(보낸 사람 제외). 좌표를 해석하거나 고치지 않는다.
- **DB에 저장하지 않는다.** 수행 기록에도 넣지 않는다([수행기록_형식.md](수행기록_형식.md)).
- 원본 영상은 받지 않는다. 서버로 오가는 것은 동작 정보뿐이다.

## 서버 쪽 한도 (확인한 값)

| 항목 | 값 | 근거 |
|---|---|---|
| 텍스트 메시지 하나의 최대 크기 | 8KB (8192바이트) | Tomcat 11.0.27 `org.apache.tomcat.websocket.Constants.DEFAULT_BUFFER_SIZE`. 이 프로젝트는 바꾸지 않았다 |
| 연결 하나의 보내기 대기 버퍼 | 64KB | `realtime.send-buffer-size` (임시값) |
| 메시지 하나 보내기 제한 시간 | 5초 | `realtime.send-time-limit` (임시값) |
| 운동방 정원 | 5명 | 지정 운동방 임시값 |

8KB를 넘는 메시지는 서버가 받지 못한다. 동작 정보 메시지는 **봉투를 포함해 8KB보다 충분히 작아야** 한다.

## 후보별 크기 실측

MediaPipe Pose Landmarker 결과 형태를 흉내 낸 값으로 JSON 크기를 쟀다(2회 측정, 차이 10바이트 이내).
MediaPipe는 한 사람당 관절 33개를 화면 좌표(`landmarks`, 0~1 정규화)와 월드 좌표(`worldLandmarks`, 엉덩이 중심 기준 미터)로 함께 낸다. 관절마다 `x`·`y`·`z`·`visibility`·`presence`가 있다.
AI 담당이 MediaPipe를 쓸지는 아직 정해지지 않았다(미확인). 다른 라이브러리라도 관절 수와 숫자 자릿수가 크기를 결정하므로 아래 표로 가늠할 수 있다.

- **보냄**: 클라이언트 → 서버 메시지 크기
- **받음**: 서버 → 다른 참가자 메시지 크기(봉투 포함)
- **서버 송신량**: 5명이 모두 같은 빈도로 보낼 때 서버가 내보내는 양 = 5 × 4 × 받음 × 빈도

| 후보 | 보냄 | 받음 | 8KB 안 | 서버 송신 10Hz | 15Hz | 30Hz |
|---|---|---|---|---|---|---|
| A. 결과 그대로 (33개, 이름 있는 객체, 원래 정밀도, 화면+월드) | 9,007B | 9,092B | **X** | 14.5 Mbps | 21.8 Mbps | 43.6 Mbps |
| B. 화면 좌표 33개만, 객체, 원래 정밀도 | 3,517B | 3,602B | O | 5.8 Mbps | 8.6 Mbps | 17.3 Mbps |
| C. 월드 좌표 33개, 배열 `[x,y,z,v]`, 소수 3자리 | 927B | 1,012B | O | 1.6 Mbps | 2.4 Mbps | 4.9 Mbps |
| D. 월드 좌표 13개(팔·다리·몸통), 배열, 소수 3자리 | 411B | 496B | O | 0.8 Mbps | 1.2 Mbps | 2.4 Mbps |

- A는 **8KB를 넘어 서버가 받지 못한다.** 라이브러리 결과를 그대로 보내면 안 된다.
- 이름 있는 객체(`{"x":…}`)를 배열(`[x,y,z,v]`)로 바꾸고 소수 3자리로 줄이는 것만으로 크기가 약 1/4로 준다(B → C).
- 소수 3자리는 월드 좌표에서 1mm, 화면 좌표에서 화면 폭의 0.1%다. 캐릭터 움직임에는 충분할 것으로 본다(3D 담당 확인 필요).

## 제안

| 항목 | 제안 | 정할 사람 |
|---|---|---|
| 좌표 | 월드 좌표 하나만 보낸다. 화면 좌표와 둘 다 보내지 않는다 | 3D |
| 관절 | 3D 캐릭터가 쓰는 관절만 **고정 순서 배열**로 보낸다. 순서 표는 이 문서에 적는다 | AI·3D |
| 숫자 | 좌표 소수 3자리, `visibility` 소수 2자리 | AI·3D |
| 빈도 | **최대 15Hz(임시)**. 서버는 상한을 넘는 메시지를 버린다(S4) | AI·PM |
| 크기 | 메시지 하나 **2KB 이하(임시)**. 넘으면 서버가 `INVALID_MESSAGE`로 거절한다(S4) | 백엔드 |

C·D 어느 쪽이든 15Hz에서 운동방 하나당 서버 송신은 1.2~2.4 Mbps다. 받는 참가자 한 명은 친구 4명 기준 약 0.2~0.5 Mbps를 받는다.
반면 B 이상(원래 정밀도의 객체)은 30Hz에서 운동방 하나가 17 Mbps를 넘는다. 프리 티어 서버에서 여러 방을 받기 어렵다.

### 메시지 모양 (제안)

기존 [실시간_메시지_형식.md](실시간_메시지_형식.md)의 봉투를 그대로 쓴다.

```jsonc
// 클라이언트 → 서버
{ "type": "POSE", "payload": { "landmarks": [[0.012, -0.531, 0.104, 0.98], [0.153, -0.402, 0.061, 0.97]] } }

// 서버 → 같은 방의 다른 참가자
{ "type": "PARTICIPANT_POSE", "roomId": 1, "participantId": 3, "sentAt": "…",
  "payload": { "landmarks": [[0.012, -0.531, 0.104, 0.98], [0.153, -0.402, 0.061, 0.97]] } }
```

- 배열 안 하나가 관절 하나이고 순서는 위의 관절 순서 표를 따른다. `[x, y, z, visibility]`다.
- 현재 운동은 넣지 않는다. 이미 `STATUS`로 전달하고 있다.
- 인식이 안 되는 동안에는 `POSE`를 보내지 않는다. 받는 쪽은 마지막 자세에서 멈추고 움직임을 지어내지 않는다.
  - 이 상태를 친구 화면에 표시할지는 아래 "정해야 할 것"에서 정한다.

### 관절 순서 (D안 예시 — MediaPipe 번호 기준)

| 순서 | 관절 | MediaPipe 번호 |
|---|---|---|
| 0 | 코 | 0 |
| 1, 2 | 왼쪽·오른쪽 어깨 | 11, 12 |
| 3, 4 | 왼쪽·오른쪽 팔꿈치 | 13, 14 |
| 5, 6 | 왼쪽·오른쪽 손목 | 15, 16 |
| 7, 8 | 왼쪽·오른쪽 엉덩이 | 23, 24 |
| 9, 10 | 왼쪽·오른쪽 무릎 | 25, 26 |
| 11, 12 | 왼쪽·오른쪽 발목 | 27, 28 |

3D 캐릭터에 손·발끝·얼굴 관절이 더 필요하면 늘린다. 33개 전부를 보내도 C안 크기(약 1KB)라 서버 한도에는 여유가 있다.

## 측정 방법

`node`로 위 네 후보의 JSON을 만들어 `Buffer.byteLength`로 쟀다. 좌표는 범위 안의 난수다(화면 좌표 0~1, 월드 좌표 ±1).

- 실제 MediaPipe 결과로 잰 값이 아니다. 숫자 자릿수만 같게 맞췄다.
- 서버 송신량은 계산값이다. 실제 지연과 처리량은 S4에서 여러 PC로 잰다.

## 정해야 할 것

| 항목 | 누구 | 메모 |
|---|---|---|
| 인식 라이브러리 (MediaPipe 여부) | AI | 관절 번호와 좌표계가 여기서 정해진다 |
| 관절 목록과 순서 | AI·3D | 위 D안 13개가 예시 |
| 화면 좌표·월드 좌표 중 무엇을 쓸지 | 3D | 캐릭터 반영은 월드 좌표가 쉬울 것으로 본다(미확인) |
| 전송 빈도 상한 | AI·PM | 임시 15Hz. S4 다중 PC 측정 뒤 확정 |
| 인식 불가 동안 친구 화면 표시 | 프론트·디자인 | `POSE`가 멈춘 것만으로 판단할지, `STATUS`에 값을 추가할지 |
| 카메라를 허용하지 않은 참가자 | 백엔드·프론트 | S4에서 `CAMERA_ERROR` 상태 참가자의 `POSE`를 중계하지 않는 방식으로 제안 |
